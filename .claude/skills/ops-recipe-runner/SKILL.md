# ops-recipe-runner（レシピ駆動オペのルーター）

運用メンバー（非PG）の「やりたいこと」を受け、レシピを軸にした4つのオペレーションへ振り分ける入口。
各ステップで **「次へ進めますか？」** と確認しながら進め、勝手に先へ進めない。

## 0. 起動時に必ず行うこと（リポジトリルートの解決）

このスキルは**任意のワークスペースから起動される**。前処理コアの実行・成果物の書き出しは
すべてリポジトリ側で行うため、**最初にリポジトリルートの絶対パスを確定する**。

```bash
echo "$OPS_RECIPE_RUNNER_HOME"
```

- 値が取れたらそれをリポジトリルートとする。
- 空なら Host に「`ops-recipe-runner` をcloneした場所」を尋ね、`~/.claude/settings.json` の
  `env` に `OPS_RECIPE_RUNNER_HOME` を設定するよう案内する（次回以降の再質問を避けるため）。

確定したら、**サブエージェントを呼ぶ際は必ずリポジトリルートの絶対パスを伝える**。
各エージェント定義のパス（`doc/...` `src/...`）はリポジトリルート相対で書かれているため、
これが無いと参照先を解決できない。

### 入力ファイルの受け渡し

Host から受け取ったCSV等は、**リポジトリの `work/` へコピーしてから**前処理を実行する
（`work/` は `.gitignore` 済み）。前処理CLIはリポジトリをカレントディレクトリとして実行する
（`.env` の読み込みがカレントディレクトリ依存のため）。

```bash
cp <Hostが示したCSVの絶対パス> "$OPS_RECIPE_RUNNER_HOME/work/"
cd "$OPS_RECIPE_RUNNER_HOME" && npm run preprocess:extract-column -- work/<file>.csv <列名> [filter]
```

**ワークフロー完了後は `work/` に置いた入力を削除する**。実務データ（本番相当）を
ローカルに残さないため。

## 1. 意図の分類（まず判定する）

| 意図 | トリガー例 | 振り分け先 |
| --- | --- | --- |
| レシピ作成 | 「レシピを作りたい」「この作業を自動化したい」 | フローA（開発パイプライン） |
| レシピ修正 | 「レシピを直したい」「テンプレを変えたい」 | フローB（軽量パイプライン） |
| チケット新規作成 | 「このレシピでチケットを作って」 | フローC（実行） |
| チケットへSQL追記 | 「既存チケットにSQLを足して」 | フローD（実行・追記） |

曖昧なら**どれかを質問**してから進む。

## 共通ルール

- 各フェーズ担当（`.claude/agents/*.md`）のDoD＝一次チェック。フェーズ完了ごとに結果を提示し、
  **「次へ進めますか？」** で承認を得てから次へ進む。
- 破壊的・外部影響（Backlog起票／更新SQLの適用）は必ず**内容提示＋承認**を挟む。
- 責務分割は `CLAUDE.md`、フロー図は `doc/architecture/`（作成=recipe-creation.md / 実行=ticket-workflow.md）。
- Backlog MCPが未接続の環境では、レシピ/テンプレSQLの実体（Backlogドキュメント）を読めない。
  `/mcp`で接続状態を確認するようHostに伝え、接続前提の作業は進めない。

## フローA：レシピ作成（開発パイプライン）

順に担当を通し、各フェーズの後に確認ゲートを置く。

1. **要件**（recipe-requirements-analyst）→ 要件シート。提出物（CSV/手作業SQL/手順書）を先に読む。合意で次へ。
2. **設計＋ドキュメント叩き台**（recipe-designer / recipe-documenter）→ 叩き台で要件を炙り出す**詳細化ループ**（収束まで往復）。
3. **実装**（recipe-implementer）→ 前処理コードは**必要なときだけ**。既存で足りればスキップ。
4. **テスト**（recipe-tester）→ 単体（前処理コードを足したら結合も）。
5. **ドキュメント確定＋レシピ作成**（recipe-documenter）→ ①レシピ ②運用ドキュメント。**レシピ静的チェック**（recipe-creation.md）。
6. **レビュー**（recipe-reviewer）→ 最終ゲート。blocker/major が無ければ完了。

→ 完了報告（レシピの所在／Backlog URL）。

## フローB：レシピ修正（軽量・影響フェーズのみ）

1. **影響範囲を特定**：何が変わるか（テンプレ文言のみ / lookup宣言 / 前処理コード / パラメータ）。
2. **影響フェーズだけ回す**：
   - テンプレ/文言のみ → ドキュメンター（レシピ更新＋静的チェック）。
   - lookup/前処理コードが要る → 設計 → 実装 → テスト も通す。
3. **レビュー（recipe-reviewer）は必ず通す**（横断の齟齬確認）。

→ 変更点と影響を提示して承認。

## フローC：チケット新規作成（実行）

`doc/architecture/ticket-workflow.md` に従う。

1. レシピ＋テンプレSQL取得、プレースホルダ種別 / lookup宣言を解釈。
2. 未確定パラメータを確認（作業者ID・処理月→基準日 等）。
3. データ由来プレースホルダは前処理（CSV抽出 / lookup）。リテラルはこの場で置換。
4. 最終SQL組み立て → **静的安全チェック**（`BEGIN/ROLLBACK`・空WHERE無し・backup・未置換 `{{...}}` 無し）
   ＋**日付確認観点**（ticket-workflow.md §5：祝日繰上・同日・起点月・クォート）。
5. SQL提示 → 承認 → Backlogへ起票 → URL報告。

## フローD：チケットへSQL追記（実行・追記）

フローCと同じ組み立て・チェックを行い、**新規起票の代わりに既存チケットへ実行SQLを追記**する。
対象チケットを特定 → 追記内容を提示 → 承認 → 追記（Backlogのコメントとして追加） → 報告。

各フローの確認済み範囲は `doc/test-summary.md` を参照。
