# テスト方針（V字モデル）

運用スクリプトは入力がある程度固定化されている。左（要件・設計）で決めた内容に対応する
テスト観点を**要件段階で先に定義**し、テスト担当はそれを過不足なく実装する。

## 責務移管による対象の変化（重要）

テンプレSQL・レシピの Backlog 移行と、日付計算・プレースホルダ置換の Agent 委譲に伴い、
**コードのテスト対象は「前処理（CSV解析・lookup）」に限定**された。生成SQLの忠実性（受入）や
日付計算（多TZ・祝日）は Agent の責務へ移り、**コードの vitest ではなく Agent の確認観点**で担保する。

| V字レベル | 観点 | 担保する場所 |
| --- | --- | --- |
| 受入 | 生成SQLが業務として正しいか（忠実再現・安全枠・未置換なし） | **Agentの静的安全チェック＋人手レビュー**（`doc/architecture/ticket-workflow.md`） |
| 結合 | DB を挟む lookup が正しく解決されるか | **vitest（結合スイート）** |
| 単体 | 前処理の純粋ロジック（CSV解析・ID抽出・lookupの組立/allowlist検証など） | **vitest（単体スイート）** |

> 日付計算の多TZ・祝日繰上は、コードから消えたため**コードテストの対象外**。
> Agent の日付確認観点（`ticket-workflow.md` の §5）で担保する。

## コードテストの2スイート

| スイート | コマンド | 対象 | 前提 |
| --- | --- | --- | --- |
| 単体 | `npm test` | 純粋な前処理（`parseCsv` ほか） | なし（純粋・高速・CI常時） |
| 結合 | `npm run test:integration` | lookup×DB（`lookup.ts` の `runLookupSteps`） | `docker compose up -d db`（seed投入済み） |

## 粒度の原則（作りすぎない・漏らさない）

- **単体を厚く**：前処理の純粋ロジックは固定値で境界まで押さえる。
- **結合は代表 1 ケース**：seed DB に対し「代表 order_id → 期待 invoice_id / sales_id」。
  多段 lookup（order → order_detail → sales）もここで確認。
- **境界・異常系は実務で起きる 1 本に限定**：例「対象 0 件」。
- **入力幅が狭い前提**を崩さない。ありえない入力のための防御的テストは足さない。

## テスト観点の記録場所

各ルーティンのテスト観点は要件シート（`doc/requirements/<name>/<name>.md`）の
「テスト観点」節に受入・結合・単体で表として残す。テスト担当はそのうち
**結合・単体を vitest に実装**し、**受入は Agent の確認観点**として `ticket-workflow.md` を参照する。
